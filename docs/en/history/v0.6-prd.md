## Product definition

Audux was defined as a completely local desktop player and personal audio knowledge manager. It
turned audio scattered across folders into a library that could be played, edited in-app, tagged,
organized into playlists, searched, transcribed, analyzed by a user-configured LLM, exported, and
backed up—without writing application metadata back into the original media.

### Target users

- Podcast, interview, and lecture collectors who need tags, playlists, and transcript search.
- Learners managing courses, language practice, and audiobooks with playback continuity.
- Creators organizing interviews and recorded source material.
- Privacy-sensitive users who require audio, metadata, and transcripts to remain local by default.

### Historical goals

1. Add one or more local audio roots and scan supported files.
2. Read embedded metadata and covers while retaining original values.
3. Play locally with seek, speed, volume, queue, and per-audio position history.
4. Edit application metadata without touching source files.
5. Organize with tags and playlists, including maintenance and export.
6. Search metadata and transcript text through SQLite FTS5 with a partial-match fallback.
7. Transcribe through local faster-whisper and preserve full text plus segments.
8. Use an explicitly configured OpenAI-compatible LLM for description and tag proposals.
9. Keep AI output as a proposal rather than overwriting user data.
10. Run scans, ASR, and AI in cancellable, retryable background tasks.
11. Provide logs, exports, index rebuild, and maintenance tools.
12. Bind the backend to loopback with restrictive CORS and local authentication.
13. Preserve playback, manual organization, and keyword search without internet access.

### Historical non-goals

Accounts, cloud/multi-device sync, online music/podcast subscriptions, social sharing, mobile apps,
default online models, automatic diarization/chapters, semantic vectors, transcript Q&A, embedded
file-metadata writes, plugins, full migration wizards, and rich-text transcript editing were
explicitly deferred at this stage.

## Product and safety principles

### Local-first storage

The database, tags, playlists, transcripts, task results, cover cache, logs, and settings lived
under the local application data directory. Original media remained in user-selected roots.

### Privacy-first providers

No audio, transcript, or metadata was uploaded by default. A remote provider required user
configuration and a warning when the endpoint was not localhost, loopback, or `.localhost`.

### Proposals do not overwrite accepted data

AI descriptions and tags were stored as suggestions. Users could accept, ignore, edit, or
regenerate them. User descriptions and tags remained authoritative.

### Database and files are separate

Titles, authors, albums, descriptions, tags, transcripts, playlists, positions, and AI results were
stored in SQLite. Removing an application record or root did not delete or rewrite original audio.

### Portability

Metadata, transcripts, playlists, and logs had explicit export formats. Later work would add managed
snapshot/restore and complete portable archives.

## Functional requirements archive

### Library roots and scanning

- Add multiple unique existing directories; enable or disable each without deleting records.
- Scan MP3, M4A, FLAC, WAV, and OGG in a background task with total, processed, imported, updated,
  missing, status, and error fields.
- Rescans update technical metadata without duplicate records; absent files become `is_missing`.
- Relink a missing record only to an existing supported file not already owned by another record.
  Preserve user metadata and refresh technical metadata and embedded cover where appropriate.

### Playback

- Play, pause, resume, stop/reset, previous, next, seek, show current/total time, set volume, and
  advance after completion.
- Support 0.75x, 1.0x, 1.25x, 1.5x, and 2.0x and remember the selected speed.
- Persist per-audio position, resume later, offer restart near the end, and reset after completion.
- Build a queue from the current list or playlist; show it in a compact popover with jump, remove,
  clear, drag ordering, and keyboard ordering.

### Metadata and cover art

- Display original, user, AI, technical-file, playback, transcript, and AI status fields separately.
- Resolve display title from user title, original title, then filename; author from user then
  original; description from user, AI, original, then empty.
- Edit `title_user`, `author_user`, `album_user`, `description_user`, `language`, and favorite state
  without modifying the file, and update search afterward.
- Prefer user-uploaded cover, then embedded cover, then default. Accept JPG/JPEG/PNG/WebP up to
  10 MB, store locally, and allow deletion of only the user cover.

### Tags

- Add multiple tags through typed, comma-separated, or existing-tag selection input.
- Keep names globally unique and many-to-many associations idempotent; track user/AI/system origin.
- Remove an association without deleting the shared tag and update search.
- Filter library results by tag together with keyword search.
- Rename tags, clean unused tags, and block deletion of used tags unless explicitly forced.

### Playlists

- Create, rename, delete, describe, and expose playlists in navigation.
- Add or remove audio without affecting the source record; preserve explicit ordering and support
  move/drag operations.
- Play continuously in playlist order and export JSON/M3U.
- Playlist deletion removes membership only, never audio, transcripts, or tags.

### Search

- Search title, author, description, tags, and transcript with SQLite FTS5 plus a partial/Chinese
  fallback.
- Combine keywords with root, tag, playlist, favorite, missing, transcript status, and AI status.
- Highlight matched fields and show transcript context with a playable time target.
- Rebuild the index deterministically from accepted source data.

### Transcripts

- Create cancellable ASR tasks only for validated library media.
- Store complete text, detected language, model/provider provenance, and ordered segments with start,
  end, and text.
- Display full text and segment timestamps; clicking a segment seeks playback.
- Export TXT, JSON, and SRT.
- Preserve segment timing during segment corrections; a full-text replacement explicitly removes
  incompatible segmentation.

### AI analysis

- Configure an OpenAI-compatible endpoint, model, key, timeout, token limit, temperature, and remote
  consent.
- Send only the selected audio's relevant metadata and transcript after explicit action.
- Require structured JSON for descriptions and tag suggestions, validate types/limits, and keep
  output separate from accepted user content.
- Create persistent pending/running/completed/failed/canceled tasks with progress, errors, retry, and
  cancellation. The UI remained interactive while work ran.

### Export, maintenance, and logs

- Export metadata as JSON/CSV, playlists as JSON/M3U, and transcripts as TXT/JSON/SRT.
- Rebuild search from database source records.
- Clean orphan tags without deleting tags still referenced by audio.
- Keep local operational logs with viewing/download support while excluding provider keys and local
  authentication secrets.
- Centralize library, ASR, LLM, appearance, maintenance, and about/version settings.

## Historical architecture

### Frontend

React owned user interaction, stateful panels, playback, and task polling. HTTP calls were
centralized rather than embedded in components. The Tauri wrapper owned native paths/dialogs and the
dynamic backend URL.

### Backend

FastAPI routes were thin, with scanning, media probing, search, tags, playlists, transcripts,
providers, tasks, and maintenance in services. Long-running work stayed out of request handlers.
SQLite/SQLModel stored application data with foreign keys, WAL, busy timeout, and FTS enabled.

### Desktop host

Tauri started a local backend sidecar on loopback, discovered a free port, supplied authentication
and the actual base URL to the frontend, and terminated child processes on application exit.
Packaging used target-native `audux-backend-<target-triple>[.exe]` sidecars.

## Historical data-model themes

- `LibraryRoot` separated configured media roots from audio records.
- `Audio` retained original and user metadata, technical fields, missing/favorite state, and
  playback history.
- `Tag` plus association tables modeled many-to-many tagging with provenance.
- `Playlist` and ordered membership separated organization from source audio.
- `Transcript` and `Segment` represented full text and playable evidence.
- `Task` represented scan/ASR/AI lifecycle and retry/cancellation.
- `Setting` held non-secret configuration; credentials required protected handling and redaction.

Later milestones replaced mutable transcript assumptions with immutable revisions, structured
issues, chapters, agent sessions/runs/citations, organization proposals/approvals, archive records,
and explicit schema markers. Those current semantics are documented in the roadmap and compatibility
contract, not this archive.

## Security and non-functional acceptance themes

- Bind only to `127.0.0.1`; allow only approved browser/Tauri origins.
- Authenticate local requests and require a client marker for unsafe methods.
- Validate all media and relink paths against trusted library roots.
- Never expose keys or local tokens in logs, errors, fixtures, exports, or screenshots.
- Preserve original files and reject schema mismatches without destructive repair.
- Keep tasks cancellable and recover interrupted persisted state at startup.
- Keep library browsing/playback responsive during scans and model calls.
- Test with temporary homes and never real `~/.audux/` data.
- Build sidecars on their target OS and verify clean startup, port conflict, normal exit, and
  uninstall behavior on Linux, Windows, and macOS.

## Transition to the current roadmap

The historical MVP+ direction became the following durable invariants:

1. Original audio is read-only and separate from application data.
2. No user content is uploaded by default.
3. Backend scope and permissions—not prompt text—authorize agents.
4. AI produces inspectable proposals and never silently overwrites accepted content.
5. Raw source, accepted content, proposals, and rebuildable indexes remain separate.
6. Playback, manual editing, keyword search, and export survive provider failure.
7. Important data is exportable, backed up, and migratable.

See the [current product roadmap](../project/roadmap.md) for implemented milestones and remaining
release acceptance work.
